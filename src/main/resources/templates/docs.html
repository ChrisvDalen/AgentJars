The AGENT.md format

An agent is a directory containing an AGENT.md. The file opens with YAML front matter describing the agent, followed by the instructions the agent runs on. Everything else in the directory — reference documents, prompt fragments, scripts — is packaged alongside it. 

---
name: Code Reviewer
description: Reviews a diff for correctness bugs, missing test coverage and needless complexity.
model: reasoning
tools: [read_file, grep, list_directory, run_tests]
tags: [review, quality, testing]
license: Apache-2.0
---

# Code Reviewer

Read the diff before the surrounding code. Report findings ranked by severity,
each with the input that triggers the defect...

Only name is required. description falls back to the first paragraph of the body when it is absent, and license falls back to a LICENSE file next to the agent or at the repository root.

Consuming an agent

Add the coordinate to your build the way you would any other dependency.

maven
gradle
sbt

Because agents are ordinary jars, everything the dependency graph already does applies to them: version pinning, transitive dependencies for agents that build on other agents, and a lockfile that records exactly which revision of an agent a build used.

Extracting agents at runtime

Agent runtimes read agents from a directory, so the jars have to be unpacked once at startup. AgentJarsExtractor walks the classpath, finds every jar carrying an agents root, and writes them into one directory. 

import com.agentjars.runtime.AgentJarsExtractor;

Path agents = AgentJarsExtractor.create().extractTo(Path.of("build/agents"));
// build/agents/code-reviewer/AGENT.md
// build/agents/release-notes/AGENT.md

Each agent keeps its own subdirectory, so two jars contributing agents with the same file names never collide. Entry names that would escape the target directory are rejected rather than written.

Publishing your own

Push your agents to a public GitHub repository, then submit it on the publish page. The registry shallow-clones the repository, finds every AGENT.md, and packages each one separately.

Two rules decide whether a repository can be packaged:

  • Agent directories may not nest. A nested agent would be packaged twice — once on its own and once inside its parent — under two different coordinates, so an overlap fails the run instead of being silently resolved.
  • Every agent needs a license. Resolution runs from most specific to least: the front matter, a LICENSE next to the agent, then the repository root. An agent that resolves to nothing is skipped and reported; the rest of the repository still publishes.

Coordinates and versions

Every AgentJar is published under the group com.agentjars. The artifactId is derived from where the agent came from: 

<org>__<repo>__<agent>

myorg/my-agents  +  agents/reviewer   →   myorg__my-agents__reviewer
myorg/my-agents  +  <repository root> →   myorg__my-agents

Each segment is lowercased and stripped of anything that is not alphanumeric, a hyphen or an underscore. A leading agents/ is dropped, so an agent's location in the repository can move between reviewer/ and agents/reviewer/ without changing its coordinate.

Versions are YYYY_MM_DD-<short-commit> — the day the agent was packaged and the commit it was packaged from. That keeps versions sortable and lets any published artifact be traced to an exact revision.

What is inside a jar

The agent's files are placed under META-INF/agents, in a directory named after the agent: 

layout

The index file marks the jar as an AgentJar so the extractor can find it on a classpath without scanning every jar. The manifest carries the agent name, its root inside the jar and the repository and path it was packaged from.

HTTP API

The registry is readable as JSON for tooling that resolves agents without scraping HTML.

Endpoint Returns
GET /api/agents?q=&tag= Every agent, filtered by free text and tag
GET /api/agents/{artifactId} One agent with its versions and dependency snippets
GET /api/agents/{artifactId}/{version}/files The file listing of one published jar
